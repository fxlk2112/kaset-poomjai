# ตรวจเทียบสิ่งที่ตกลงก่อนสร้างกับเว็บปัจจุบัน

วันที่ตรวจ: 24 พฤศจิกายน 2569 · ผล: **ยังไม่ตรงครบทั้งหน้าตาและขั้นตอนใช้งาน**

ตรวจที่ commit `c4d8798` บน branch `codex/projects-trials-v1` โดยย้อนอ่านแชต “วางแผนเว็บเก็บ KPI” ช่วงออกแบบก่อนเริ่มเขียนโค้ด เปิดภาพร่างเดิม และทดลองหน้าปัจจุบันด้วยข้อมูลตัวอย่างในเครื่อง ไม่ใช้จำนวนข้อทดสอบที่ผ่านเป็นหลักฐานว่าทำครบตามแบบ

## เกณฑ์ที่ใช้

เกณฑ์หลักคือสิ่งที่ผู้ใช้เลือกและตอบรับ: ใช้เว็บ FARMULTIMATE ปัจจุบัน เพิ่มเมนูงานและการทดลอง รวมโครงการ/งานย่อย/ผลทดลอง ไม่คิดคะแนน KPI พิมพ์สิ่งที่จะทำแล้วระบบช่วยจัดร่างที่แก้ได้ บันทึกผลและรูปตามงาน ทำเล่มสรุป และเชื่อมงานฟาร์มกับรอบปลูก/ต้นทุนโดยไม่กรอกซ้ำ

ใช้ภาพร่างรุ่นหลังเป็นเกณฑ์เมื่อมีการปรับรายละเอียดต่อจากภาพก่อน เช่น หน้าบันทึกผลรุ่นล่าสุดเป็นตัวเลือกงานด้านซ้ายและพื้นที่กรอกด้านขวา จึงไม่ตัดสินว่าต้องมีรายชื่อทุกโครงการซ้ำอยู่ด้านซ้ายในทุกหน้า เพียงเพราะภาพแนวคิดช่วงแรกเคยมีสามคอลัมน์

## ข้อผิดพลาดเรื่องหลักฐานในรายงาน

`projectReportSnapshot()` ใน `js/project-workspace.js:132` เก็บ `t.note` กับ `t.photos` ของกิจกรรม แต่ไม่ดึง `doneNote` และ `donePhotos` ซึ่งใช้บันทึกผลเมื่อทำงานเสร็จใน `js/app.js:4333` ดังนั้นกิจกรรมที่ถ่ายรูปหรือเขียนสรุปตอนกดทำเสร็จอาจไม่มีหลักฐานเหล่านั้นในเล่มโครงการ

ยืนยันด้วยการเรียกฟังก์ชันจริงในสภาพแวดล้อมแยก ใช้ข้อมูลสมมติที่มีรูปหลังทำหนึ่งรูปและหมายเหตุหลังทำ ผลรายงานกลับมีศูนย์รูปและข้อความก่อนทำ หลักฐานอยู่ใน `qa/requirements-audit/read-model-check.json` ไม่มีการเขียนข้อมูลทดสอบนี้ลงบัญชีในเบราว์เซอร์

อีกประเด็นคือรายงานดึงข้อมูลเดิมทั้งหมดของการทดลองที่เชื่อมเมื่อยังไม่ผูกงานย่อย หน้าปัจจุบันแสดง 169 ค่าวัดทั้งที่งานที่เลือกมีค่าวัดเชื่อมหนึ่งรายการ นี่อาจเหมาะกับการนำผลเดิมมาใช้ แต่ยังไม่มีเครื่องมือระบุขอบเขตชุดข้อมูล/ช่วงเวลาเข้าเล่มตามภาพ จึงต้องทำให้ผู้ใช้ตรวจเลือกได้ชัด

ร่างกิจกรรมและแปลง/รอบที่เลือกไว้มีอยู่จริง แต่หน้าแรกยังเป็นตัวเลือกงานเต็มหน้าและต้องไปต่อสามขั้น ต่างจากหน้ากระชับที่เห็นวัสดุ ค่าแรง ถ่ายรูป และยอดรวมร่วมกันตามภาพล่าสุด ร่างเดิมคงไว้ ไม่ได้สร้างกิจกรรมหรือตัดสต็อก

## สิ่งที่ควรแก้ตามลำดับ

1. ปิดช่องว่างระหว่างข้อความกับแผน: สัปดาห์ วันเริ่ม ตัวอย่าง ตัวชี้วัด ผู้รับผิดชอบ และการแก้/เรียงร่าง
2. ทำหน้าบันทึกผลตามแบบ: ตารางบนคอม กรอกทีละต้นบนมือถือ ร่างอัตโนมัติ เหตุการณ์ และรูปแยกรายภาพ
3. ทำเล่มให้ครบตามหลักฐาน: แก้รูป/หมายเหตุหลังทำที่ตกหล่น แล้วต่อการจัดหัวข้อ เลือกภาพ เวอร์ชัน และส่งออก
4. ปรับฟอร์มกิจกรรมมือถือให้ตรงหน้ากระชับ โดยรักษาการคำนวณต้นทุนและสต็อกเดิม

## ขอบเขตและข้อจำกัดของการตรวจ

- อ่านประวัติแชตและภาพที่เลือกจริง ไม่อนุมานจากข้อความส่งงานครั้งก่อนอย่างเดียว
- ตรวจหน้าปัจจุบันและโค้ด ไม่มีการแก้โค้ดแอปหรือใช้ข้อมูลจริงภาคสนาม
- ไม่มีการสร้างโครงการ กิจกรรม ค่าวัด หรือรายงานฉบับใหม่ มีเพียงร่างข้อความทดสอบที่ยังไม่สร้างโครงการในบัญชีตัวอย่าง
- ไม่ได้รันทดสอบทั้งชุดใหม่ เพราะรอบนี้ไม่ได้แก้โค้ด; ผล 620/620 จากรอบก่อนครอบคลุมสิ่งที่เขียนไว้ แต่ไม่ได้ยืนยันข้อกำหนดที่ยังไม่ถูกเขียน
- ไม่ได้ตรวจ cloud sync, ความพร้อม production, กล้องจริง, offline round trip หรือ native PDF/Word output ใหม่
- การมีชื่อช่องและขนาดมือถือที่ไม่ล้นเป็นข้อดี แต่ไม่ได้ตรวจ keyboard/screen reader/contrast ครบ จึงไม่อ้างว่า accessibility ผ่านทั้งหมด
- ไม่มีการ push, deploy, migration หรือ hardware action
